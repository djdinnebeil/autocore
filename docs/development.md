# Development

How to extend Auto Core: shared protocols, runtime commands, and new component projects.

## Shared folder

The `app/shared` folder contains protocols shared by the main application and component executables. Reusable runtime facilities such as paths, logging, and named pipes are provided by the core DLL under `app/core`.

The C++23 module catalog is [modules.md](modules.md).

| Folder or Module | Purpose |
| --- | --- |
| `command_registry.ixx` | Stores and resolves runtime keymap command names. |
| `itunes_protocol.ixx` | Defines iTunes-component messages. |
| `journal_protocol.ixx` | Defines journal-component messages and keymap command tokens. |
| `slash_protocol.ixx` | Defines Slash recycle-bin command names. |
| `spotify_protocol.ixx` | Defines Spotify-component messages. |
| `taskbar_config_protocol.ixx` | On-demand discovery protocol for `taskbar_config.exe`. |
| `taskbar_protocol.ixx` | Defines the Main-to-`taskbar_ac.exe` control pipe and authority command names. |
| `wake_protocol.ixx` | Defines wake-component messages. |
| `writer_protocol.ixx` | Defines writer-component messages. |

## Registering runtime commands

To make a function available to the keymap, register it with the appropriate `runtime_commands::register_with` function. Auto Core refreshes `dist/keymap/keymap_commands.txt` from the command registry at startup, plus parsed `journal_choices.ini` alias names from the configured journal data directory. Per-component catalogs live in `dist/keymap/components/`. `journal.keymap_commands.txt` also lists those alias names. Taskbar `activate_*` names for configured programs are registered from `taskbar/applications/*.ini` and do not need a Main `register_with` entry.

The command registry is a process-lifetime static built in this order: test commands, main, dash, iTunes, journal, slash, Spotify, taskbar component, writer, then `taskbar_runtime_commands` last so an INI `activate_*` cannot override a reserved Main name. Duplicate `add` / `add_factory` throws `std::logic_error` and is fatal. Taskbar INI name collisions skip instead of throwing.

`get_runtime_command_names()` and `get_runtime_command_autocomplete_values()` exist on `auto_core.main.keymap.runtime` but have no in-repo callers; the autocomplete file is written from the registry directly.

Mappings in `dist/keymap/bindings.ini` are the key map. If `bindings.ini` is missing, Main writes a seed of every `key_codes` name (`numpad_0` / `numpad_1` filled, others `{, }`). If workspace creation or file load fails, Main installs a two-key emergency map in memory and does not rewrite an existing `bindings.ini`. A generic sample is [`defaults/keymap/bindings.ini`](../defaults/keymap/bindings.ini). See [configuration.md](configuration.md).

## Defaults vs live files

A public clone should not contain another person's keymap, journal print-choice table, or machine-specific config. `dist/` is gitignored. Tracked files live under [`defaults/`](../defaults/) (repo `defaults/X` is the sample for runtime `dist/X`):

- [`defaults/journal/journal_choices.ini`](../defaults/journal/journal_choices.ini) — live `dist/journal/journal_choices.ini`
- [`defaults/keymap/bindings.ini`](../defaults/keymap/bindings.ini) — live `dist/keymap/bindings.ini` (Auto Core writes a seed if missing)
- [`defaults/config/*.ini`](../defaults/config/) — live `dist/config/*.ini` (Auto Core writes portable defaults if missing)
- [`defaults/server/`](../defaults/server/) — shipped `dist/server/` pages (copied at build)

Auto Core does not read `defaults/`. A missing live `journal_choices.ini` is written once from the portable sample. Copy other defaults by hand when you want those bytes. `*.local.ini` / `*.local.ixx` are gitignored and are not loaded.

If `journal_choices.ini` is missing, Auto Core writes the sample aliases once. Lines are `name = factory_expression`. Main expands an alias only when `bindings.ini` uses that name. Parsed alias names are written to `keymap/keymap_commands.txt` and `keymap/components/journal.keymap_commands.txt`. Do not commit the live alias file. Per-program taskbar INIs live under the configured taskbar data directory (portable default gitignored `dist/taskbar/applications/`) and are generated by `taskbar_config.exe`.

## Main process session

`auto_core.exe` constructs `ac::Component auto_core`, then
`ac::main::components::initialize()`:

1. Start `taskbar_ac.exe`, wait up to five seconds for `taskbar_ready`, then up to five seconds to connect to the snapshot authority. Failure is non-fatal.
2. Create pipe servers for journal, Spotify, iTunes, wake, and writer.
3. Start those children and `server_ac.exe`.
4. Wait up to five seconds for `journal_ready` and `writer_ready`. Writer
   ready-wait failure is logged. Keymap still registers writer names; invoke
   checks `pipe.valid()`. The journal ready result is ignored.

The returned `Session` is RAII: its destructor stops the taskbar client. Child
pipe shutdowns run from `close_program()` before `WM_QUIT`. Dash is launched
on demand (`launch_dash`); Slash is one `slash_ac.exe` process per command.
`launch_journal_config` is the same on-demand shape: Main starts
`journal_config.exe` with `CREATE_NEW_CONSOLE` and does not send a pipe
request. Journal parameterized names register as factories that forward
`make_print_choice(...)` and `print_and_insert_into_journal(...)` on
`ac_journal_pipe`.

Process lifetime, hook, F-lock, and crash restart are in [main.md](main.md).

## Adding a new component

Create the project inside the `app/components` directory.

### 1. Create the component project

Create the new Visual Studio project under:

```text
app/components/<component-name>/
```

Use an existing component project as a template when possible.

### 2. Import AutoCore.props

Add this import (copy from a sibling `.vcxproj`). Tools nested one folder deeper use an extra `..\`:

```xml
<ImportGroup Label="Shared">
  <Import Project="..\..\build\AutoCore.props" />
</ImportGroup>
```

Place it after `Microsoft.Cpp.props`. That is the only directory setup. The props file is repo-relative; do not edit it after a clone. It supplies `app\core\include` (`ac_api.hpp`), `third_party\<dependency>\include` and `\lib` (vendor headers and import libraries; `\bin` DLLs copied to `dist\`), `out\core` then `lib` (`auto_core.lib`), `IntDir` (`out\obj\<project>\`), and application `OutDir` (`dist\`).

### 3. Project settings that stay in the vcxproj

Set `TargetName` to `<component>_ac` for short child process names
(`dash_ac`, `journal_ac`, `logger_ac`, and the same pattern for `server`,
`slash`, `taskbar`, `wake`, and `writer`). Leave `auto_core`,
`spotify_oauth`, `journal_config`, `server_config`, `taskbar_config`, and
`writer_config` unsuffixed. iTunes and Spotify already follow this
(`itunes_ac`, `spotify_ac`).

Add the Auto Core DLL import library, plus any vendor libraries that exe uses:

```text
auto_core.lib
```

In Visual Studio: Linker → Input → Additional Dependencies.

Add the core `.ixx` files this component `import`s to `ClCompile`. Do not set Additional Include Directories or Additional Library Directories for those paths.

### 4. (Optional) Local junction for `out\obj`

A clone does not need a symlink. If you want intermediate objects elsewhere on your machine, create a directory junction to `out\obj` yourself and keep it out of git.

### 5. Reference shared resources

If your component uses a resource image or manifest, reference the shared resource file:

```text
..\..\resources\resource.rc
```

See [building.md](building.md) for solution paths and build order.

### 6. Component session

Each executable constructs an `ac::Component` with its name, then calls `connect_to_logger()`. Worker threads should enter through `ac::thread::run_with_exception_handling` so an escaped exception is logged instead of terminating the process.
